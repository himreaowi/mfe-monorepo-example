# Guardrails

| Command      | Runs                                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------------------- |
| `pnpm check` | `check-versions` + `check-apps` + `check-packages` + `check-env` (`tools/scripts`, a few hundred ms) |
| `pnpm lint`  | `pnpm check`, then ESLint in every project (incl. Nx module boundaries)                              |

Run one check only: `node tools/scripts/bin/check.js --only versions` (or `--only apps`,
`--only packages`, `--only env`).
Errors fail the command; warnings are printed but do not fail. Every message starts with
`[check/rule]`; find the rule below.

## check-versions (dependency tiers, D4)

Background and commands: [adding-dependencies.md](adding-dependencies.md). Only `dependencies`,
`devDependencies` and `optionalDependencies` are checked; `peerDependencies` are compatibility
ranges and may stay ranges.

| Rule                         | Fails when                                                                                                                                                                                                       | Fix                                                                                                                                              |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `tier1-pinned`               | an app/package pins react, react-dom or react-router instead of `catalog:`                                                                                                                                       | `"react": "catalog:"` (or `pnpm --filter <app> add react@catalog:`). A different major needs an isolated mount-contract module, not an exception |
| `catalog-bypassed`           | a catalog package (e.g. `typescript`) is written with a version instead of `catalog:`                                                                                                                            | `pnpm --filter <app> add <pkg>@catalog:`, or add a justified entry to `version-exceptions.json`                                                  |
| `shared-not-in-catalog`      | the same third-party package is used by 2+ workspace packages without the catalog                                                                                                                                | add `<pkg>: <version>` under `catalog:` in `pnpm-workspace.yaml`, then `pnpm --filter <each user> add <pkg>@catalog:`                            |
| `exception-expired`          | a `version-exceptions.json` entry's `expires` is before today                                                                                                                                                    | move the app back to `catalog:` and delete the entry, or renew it (new date + reason, reviewed)                                                  |
| `exceptions-malformed`       | the file is not `{ "exceptions": [...] }`, a field is missing/empty/unknown, the date is not a real `YYYY-MM-DD`, the reason is under 10 characters, `app` is not a workspace package, or an entry is duplicated | fix the entry as the message says                                                                                                                |

| `tier1-drift`                | `TIER1` (`tools/scripts/src/tiers.js`) differs from `TIER1_SINGLETONS` (`packages/platform/webpack-config/src/tier1.js`)                                                                                         | change both lists together                                                                                                                       |
| `tier1-missing`              | a tier-1 package is not in the default catalog (or `@org/ui` / `@org/auth` is not a workspace package)                                                                                                           | add it to the catalog                                                                                                                            |
| `catalog-missing`            | `"<pkg>": "catalog:"` but the catalog has no entry for it                                                                                                                                                        | add the entry to `pnpm-workspace.yaml`                                                                                                           |

The shell's layout is protected by two of these rules: a remote cannot import it (`app-import`:
apps never import each other) and cannot restyle it through page-wide custom properties
(`remote-global-tokens`). There is no rule against a remote rendering a `<header>` or `<nav>`:
inside the shell a remote renders within `<main>`, where those are ordinary page sections (an
in-page nav is legitimate), and the remote's standalone chrome is its own `StandaloneLayout`.

## check-packages (where code lives, the import table)

Background, the decision ladder and the full import table: [where-code-goes.md](where-code-goes.md).
Remotes and shells of zone Z may use `apps/Z/libs/*`, `packages/common/*` and
`packages/platform/*`; `apps/Z/libs/*` the same, never apps; `packages/common/*` only common and
platform; `packages/platform/*` only platform. Never the other zone.

| Rule                      | Fails when                                                                                                                                        | Fix                                                                                                                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `package-boundaries`      | a package.json dependency or an import in `src/` (by package name or relative path) breaks the import table                                       | the message names the target: `packages/common/<capability>` (both zones, public), `apps/<zone>/libs/<capability>`, or pass the value in |
| `package-location`        | a `package.json` in `packages/` outside `platform/<name>` / `common/<capability>`, or an item in `apps/<zone>/libs/` that is not a library folder | move it; create libraries with `pnpm gen:package <common\|zone> <capability>`                                                            |
| `package-name`            | two workspace packages share a name (e.g. a zone library and a remote of the same zone)                                                           | rename one                                                                                                                               |
| `library-name`            | a library's name does not match its folder (`@org/common-<capability>`, `@org/<zone>-<capability>`)                                               | rename the package or the folder                                                                                                         |
| `library-tags`            | the Nx tags do not follow the folder (`zone:<zone>` + `type:lib`; `type:common`; platform `type:package`)                                         | set the tags the message prints                                                                                                          |
| `library-shape`           | a library has an `mfe` block (port, federation name), a webpack config, or no `src/index.ts`                                                      | remove them / add the front door; libraries are bundled by the apps that import them                                                     |
| `library-component-files` | a library's `src/components/<Name>/` is not PascalCase or lacks `<Name>.tsx` / `<Name>.test.tsx`                                                  | one folder per component (`<Name>.module.scss` when styled, stories optional)                                                            |

## ESLint (in every project, `pnpm lint`)

`@org/eslint-config` adds two boundary rules:

- **`@nx/enforce-module-boundaries`** with the tags above (the import table of
  [where-code-goes.md](where-code-goes.md); a test in `tools/scripts` keeps it equal to
  `package-boundaries`):
  - `zone:intranet` must not depend on `zone:internet`, and vice versa
  - `type:remote` and `type:shell` may only depend on `type:lib`, `type:common`, `type:package`
    (and `type:tool`), so a remote never imports a remote or a shell, and a shell never imports a
    remote
  - `type:lib` (`apps/<zone>/libs/*`) may only depend on `type:lib`, `type:common`, `type:package`
  - `type:common` (`packages/common/*`) may only depend on `type:common` and `type:package`
  - `type:package` (`packages/platform/*`) may only depend on `type:package`
  - `type:tool` may depend on packages and tools
  - relative imports into another project fail with "Projects cannot be imported by a relative or
    absolute path"
- **`no-restricted-imports`** for the apps' package names, read from the workspace
  (`apps/<zone>/<portal>/<folder>/package.json`, not `apps/<zone>/libs/`). Nx maps a package
  import to a project only when that package declares `exports`/`main`, which apps do not, so
  app imports by name are blocked here. Zone libraries share the `@org/<zone>-` prefix and are
  imported by name.

Fix: move the shared code into a library ([where-code-goes.md](where-code-goes.md)) and depend on
it with `workspace:*`.

When ESLint reports a boundary violation, Nx may also print `Error reading "tsconfig.base.json"`.
That is noise from the rule's fix suggestion (this repo has no `tsconfig.base.json`); the real
error follows.

## At runtime

Even if all of the above were bypassed, a remote built against a different tier-1 version fails
to load (Module Federation `strictVersion`) and the shell shows `RemoteFallback` for that route
only.
